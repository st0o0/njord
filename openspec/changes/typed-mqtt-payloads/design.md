## Context

Payload assembly today: `StatePayloadBuilder` (`FromAlerts`, `FromDerived`, `FromTrends`, `FromIndices`, `FromConsensus`) builds `JsonObject`s; `HorizonProjection` (Njord.Weather, no Njord references) builds forecast horizon JSON strings and is called from `MqttStatePublisher` and `PollPipelineSpec`. Golden masters already exist for every payload kind (`StatePayloadGoldenMasterSpec.*.verified.txt`), so output can be proven byte-identical. FunkArr (reference repo) uses manual internal mapper extensions, one record per file and a mapper test per mapper; it has no source generator and no unknown-enum fallback. njord already uses a source generator in `Njord.OpenMeteo`.

## Goals / Non-Goals

**Goals:** typed records for every payload, explicit mappers, one serializer setup, deterministic key order, identical output in step 1, deliberate corrections in step 2.

**Non-Goals:** see proposal.

## Decisions

1. **Layout.** `Njord.Mqtt/Payloads/<Name>Payload.cs`, one sealed record per file: `AlertPayload` (+ one derived record per alert-details type), `DerivedHorizonPayload`, `DerivedMetaPayload`, `TrendPayload`, `IndexDayPayload` (+ envelope members), `ConsensusHorizonPayload`, `ForecastHorizonPayload`. Mappers are `internal static` extension classes grouped per domain like the existing gRPC mappers (`Njord.Grpc/Mapping/AnalysisProtoMappings.cs`): `AnalysisPayloadMappings`, `ConsensusPayloadMappings`, `ForecastPayloadMappings` in `Njord.Mqtt/Mapping/`, with `ToPayload()` per domain result. Presentation work (rounding, the `"+Nh"` text, key derivation) happens in the mappers; payload records stay plain data. Enum conversion always goes through exhaustive switches / `ToWireName()`, never casts (FunkArr casts `(ApiModels.MediaType)(int)item.Category` in places; we do not copy that). Tests reach internals through `InternalsVisibleTo` for `Njord.Mqtt.Tests` (check the csproj; add if missing).
2. **Serializer.** One `MqttPayloadJsonContext : JsonSerializerContext` (source generator, `snake_case_lower`, no indentation, `JsonIgnoreCondition.Never` so null policy is explicit per property). Enum-valued members are typed as the domain enum with a converter that writes `ToWireName()`; no `ToString()`. Alternative (reflection-based options as in FunkArr) rejected: njord already has the generator pattern and the payloads are on a hot publish path.
3. **Key order is part of the contract.** `JsonObject` keeps insertion order and the snapshots are text. Fixed-shape records serialize in property declaration order, which is arranged to match today's order. Registry-driven payloads (consensus horizon, trend, forecast horizon) use a custom `JsonConverter` that writes the ordered entries first and the fixed members after them (consensus `_spread`/`_agreement` last), reproducing today's order. `[JsonExtensionData]` is rejected for these: it emits fixed members first and would change the order.
4. **Alert details.** `AlertPayload` is a base record with the common members (`severity`, `confidence`, `trigger_value`, `threshold`, `peak_value`, `hours_until`, `duration_hours`); each details type has a derived record adding its members. Serialization uses `[JsonDerivedType]` without a discriminator (serialize-only) so derived members follow the base members, as today. If the generator cannot do this, fall back to a per-type converter; decided in the first spike task.
   Spike result (task 1.1): the source generator handles all three. (a) `[JsonDerivedType]` without a discriminator serializes derived members, but it writes them before the base members; `[JsonPropertyOrder]` with negative values on the base members puts them first again, so no per-type converter is needed and the 15 derived records (14 types plus `NoDetails`) stay plain. The common members are non-required `init` properties set with a `with` expression in the mapper. (b) A custom `JsonConverter` (via `[JsonConverter]` on the record) works with the generated context; the converters write the ordered entries first and the fixed members after them by hand. (c) Enum members use a small `WireNameConverter<TEnum>` subclass per enum that writes `ToWireName()`; it works on nullable enum properties too. Naming policy `SnakeCaseLower` is correct except for digit-bearing names (`hours_below_1000m`, `hours_above_20`), which carry explicit `[JsonPropertyName]`.
5. **Dynamic keys come from typed registry access.** Consensus keys use `ParameterDef.JsonKey` and a `ModelsKey` helper (`{JsonKey}_models`) on the payload type; trend keys use a `TrendKey` value derived from the parameter in one place (replacing the inline `Replace("_2m", "")`), tested against all registered trend parameters. No string literals for parameter names in the mappers (AGENTS.md: typed `ParameterRegistry` properties).
6. **Forecast horizon.** `HorizonProjection` returns `HorizonProjectionResult` entries (`Horizon`, ordered list of `(ParameterDef, double? Number, string? Text)`), no JSON. `ForecastHorizonPayload` wraps the entries; its converter writes `JsonKey` → number/text. Missing values are not entries (omitted). `StatePayloadBuilder.BuildPerHorizon` and `PollPipelineSpec` are adapted.
7. **Rounding moves into the mappers** (`Math.Round(x, 2)` etc., values and digit counts unchanged).
8. **Null policy (step 2).** Forecast horizon payloads omit absent values (existing `mqtt-egress` rule). Enrichment payloads (alerts, derived, trends, indices, consensus) write explicit `null` for a known field without a value. Alerts therefore start emitting `peak_value`, `hours_until`, `duration_hours` as `null`. Alert detail members that are nullable follow the same rule. This amends the main spec sentence "never carry placeholder values", which already disagrees with derived/trends/consensus today; note that a consumer cannot tell "model has no value" from "feature did not run" by `null` alone, which is why features without a result still publish nothing.
9. **`soil_frozen` boolean (step 2).** `IceDetails.SoilFrozen` serializes as `true`/`false`. `earliest_frost` stays `"+Nh"` text (non-goal).
10. **Ordering of work.** Step 1 must leave all existing golden masters unchanged; step 2 changes only the alert, ice and null-related snapshots, each diff reviewed.

11. **Boundary rule (like FunkArr).** FunkArr keeps wire/API models and their mappers in the adapter projects and keeps domain projects free of wire types. For njord the adapters are `Njord.Grpc` (already `Mapping/` + protos) and `Njord.Mqtt`. Rule: a type whose name or namespace contains `Mqtt`, or that exists only to serve MQTT, lives in `Njord.Mqtt`, with this allow-list in `Njord.Core`: `MqttOptions`, `MqttOptionsValidator`, the `ConfigReloadPolicy` entry, `IMqttConnectionActor`, `IMqttStatePublisher`, `MqttHealthSnapshot`/`NjordHealthMonitor.Mqtt`. Reason for the allow-list: the config layer and the shared health monitor are cross-feature and feature libraries may not reference each other.
12. **What moves.** `Njord.Messages/Mqtt/{MqttConnected,SubscribeInbound,MqttInboundMessage}` are used only by `MqttConnection` and its specs, so they become internal actor messages in `Njord.Mqtt/Actors/` (`Njord.Messages` is the cross-project contract and keeps no MQTT folder). `Njord/Health/MqttConnectionHealthCheck` moves to `Njord.Mqtt/Health/` and is registered by `MqttSetupContainer` instead of the host's `CoreSetupContainer` (which stops reading `MqttOptions` for it); the project needs the health-check abstractions package/framework reference, added with `dotnet add package`, versions only in `Directory.Packages.props`. `HorizonProjection` keeps the pure horizon selection in `Njord.Weather` (reusable domain logic) but loses all JSON; the wire form is `Njord.Mqtt`.
13. **Folder layout of `Njord.Mqtt`.** `Payloads/` (wire records), `Mapping/` (`ToPayload()` extensions), `Serialization/` (`MqttPayloadJsonContext`, converters), `Topics/` (`TopicScheme`, `TopicSlug`), `Actors/` (`MqttConnection`, `MqttStatePublisher`, actor messages), `Health/`, `Transport/`, `Configuration/`, `Telemetry.cs`, `StatePayloadBuilder` as the thin entry. Namespaces follow folders; only the moves needed for this layout, no behaviour change.
14. **Enforcement.** A new ArchUnitNET/reflection spec in `Njord.Architecture.Tests` fails when a type with `Mqtt` in its name or namespace is declared outside `Njord.Mqtt` and not on the allow-list, and when `Njord.Messages`, `Njord.Weather`, `Njord.Pipeline` reference `System.Text.Json.Nodes` for MQTT. Step 0 is done first, as a pure refactor, with the whole suite green before payload work starts.

15. **Enum conversion convention.** Enum to enum and enum to wire text are written as extension methods (`ToWireName()`, `ToProto()`, `ToDomain()`, `ToTopicSegment()`) with an exhaustive `switch` expression whose default throws `ArgumentOutOfRangeException`, next to the enum or in the owning adapter's `Mapping/` folder. No `(TargetEnum)(int)source` casts (renumbering silently changes meaning), no `Enum.Parse/TryParse` and no `ToString()`-derived text for values that leave the process. Parsing of user-written configuration (`ParameterRegistry` group names) and enum names in validation messages are input handling, not conversion, and stay as they are. Existing offenders: `AlertTypeExtensions.ToTopicSegment` has a `ToString().ToLowerInvariant()` fallback arm, `EnrichmentKindExtensions.ToWireName` is `ToString().ToLowerInvariant()`; both become explicit switches with unchanged outputs, pinned by a spec over all members. A source-scan spec in `Njord.Architecture.Tests` (same style as `DisabledTestArchitectureSpec`) rejects `.ToString().ToLower`/`ToUpper` on enums and `Enum.TryParse`/`Enum.Parse` in production code outside an allow-list (`ParameterRegistry`).

## Risks / Trade-offs

- Source generator vs polymorphic/flattened alerts or custom converters → spike first (task 1.1), fallback documented in decision 4.
- Custom converters re-implement ordering by hand → covered by the byte-identical golden masters and a per-converter spec.
- Step 2 is a wire break for user automations on retained topics → listed in release notes via the `feat!` commit; `docs/mqtt-reference.md` documents the new rule.
- Namespace moves touch many `using`s in tests (`Njord.Mqtt.Tests`, `Njord.Tests`) → mechanical, do it in one commit-sized step before the payload work.
- `HorizonProjection` API change touches Weather and Pipeline tests → small, mechanical.
